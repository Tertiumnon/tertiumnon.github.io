# package.json, package-lock.json и семантическое версионирование: почему это критично знать

Если вы когда-нибудь видели в коде `npm install` и потом полтора часа ломали голову, почему всё работает у вас локально, но падает на продакшене, эта статья для вас. Вероятно, это была проблема с версиями зависимостей — и именно её решает правильное понимание семантического версионирования и lock-файлов.

## Зачем вообще версионирование

Представьте: вы написали приложение на React 18.2.0, и всё работает. Через месяц выходит React 18.3.0. Должны ли вы автоматически получить это обновление? Это зависит от того, что в нём изменилось. Если там только баг-фиксы — скорее всего, безопасно. Если там [breaking change](https://docs.npmjs.com/about-semantic-versioning/), который ломает половину вашего кода — нет.

Вот именно для этого и существует [семантическое версионирование (semver)](https://semver.org/). Это стандарт, который говорит: номер версии несёт информацию о том, что в пакете изменилось.

## Семантическое версионирование: MAJOR.MINOR.PATCH

Версия состоит из трёх чисел: `MAJOR.MINOR.PATCH`. Например, `1.2.3`.

- **MAJOR** (первая цифра) — изменения, которые **ломают совместимость** (breaking changes). Если вы обновились с 1.x.x на 2.x.x, готовьтесь к тому, что часть кода может перестать работать.
- **MINOR** (вторая цифра) — **новые возможности**, но в обратно совместимом виде. Обновление с 1.2.0 на 1.3.0 должно быть безопасным.
- **PATCH** (третья цифра) — **баг-фиксы**. Обновление с 1.2.3 на 1.2.4 — это просто исправления.

[Официальная спецификация semver](https://semver.org/) выражает это так: увеличивайте MAJOR для несовместимых изменений, MINOR для обратно совместимых новых функций и PATCH для обратно совместимых баг-фиксов.

**Пример:** TypeScript — контрпример. Согласно официальной философии, [TypeScript явно не следует semver](https://dev.to/_d7eb1c1703182e3ce1782/npm-vs-pnpm-vs-yarn-which-package-manager-should-you-use-in-2026-3o3o) и вводит breaking changes в MINOR-релизах. Это означает, что обновление TypeScript с 5.3.0 на 5.4.0 может сломать вашу сборку — и всё будет формально правильно по версии, но не по semver-стандарту. Мораль: даже major-версии не гарантируют, что какой-то конкретный пакет ей следует.

## Версионирование в package.json: символы и операторы

Вот тут и начинается веселье. Когда вы пишете версию в `package.json`, можете использовать разные операторы. Каждый говорит npm, какие обновления искать при установке.

### Точная версия (без символов)

```json
{
  "@prisma/client": "6.19.3"
}
```

Это означает: установи **точно** версию 6.19.3, не выше, не ниже. Плюсы: абсолютная предсказуемость. Минусы: если выходит 6.19.4 с критическим баг-фиксом, вы его не получите, пока не обновите `package.json` вручную. А если вы забудете про это... ну, понимаете.

### Каретка (^) — подстраховка с минором

```json
{
  "@prisma/client": "^6.19.3"
}
```

Каретка говорит: обновляй MINOR и PATCH в пределах текущего MAJOR. То есть 6.19.3 → 6.20.0 → 6.99.9 — всё окей. Но 7.0.0 — уже нет. Это **дефолт** в npm, когда вы пишете просто `npm install <package>` без флагов.

**Почему это хорошо:** новые возможности (MINOR) должны быть совместимы, так что обновляться безопасно. Баг-фиксы (PATCH) вообще не требуют беспокойства.

**Почему это может быть проблемой:** а что если пакет нарушает semver? Или что если транзитивная зависимость какой-то непопулярной библиотеки получила breaking change в "minor"-версии? Вот почему существуют lock-файлы.

### Тильда (~) — только патчи

```json
{
  "@prisma/client": "~6.19.3"
}
```

Тильда консервативнее: обновляй только PATCH в пределах текущего MINOR. То есть 6.19.3 → 6.19.4 → 6.19.99 — окей. Но 6.20.0 — нет.

**Когда это полезно:** если вы работаете с очень нестабильной библиотекой, где даже minor-версии могут сломать много. Минус: вы упускаете новые фичи.

### Больше (>) и меньше (<)

```json
{
  "express": ">4.17.0",
  "lodash": "<5.0.0"
}
```

Это буквально то, что написано: установи любую версию строго больше 4.17.0 или строго меньше 5.0.0. С `>=` и `<=` то же самое, но включаешь граничное значение.

**Когда это пригодится:** редко. Обычно комбинируешь: `"express": ">=4.17.0 <5.0.0"` означает "от 4.17.0 до 4.99.99".

### Равно (=)

```json
{
  "react": "=18.2.0"
}
```

Это то же самое, что просто `"react": "18.2.0"`. Точная версия, не более.

### Звёздочка (*)

```json
{
  "react": "*"
}
```

Принимай **любую** версию. Включая 0.x.x-alpha-dev-666. Это редко встречается в сопровождаемом коде в продакшене, потому что это просто рулетка.

### Комбинирование

[Согласно npm документации](https://docs.npmjs.com/about-semantic-versioning/), можно комбинировать операторы через пробел:

```json
{
  "react": ">=18.0.0 <19.0.0"
}
```

Это означает: от 18.0.0 до 18.99.99 включительно. Практически эквивалентно `^18.0.0`, но явно.

## Package-lock.json: почему это ваш спасатель

Вот сценарий без lock-файла:

1. **День 1, машина А (ваша локалка):** вы пишете `^@prisma/client: 6.19.3` в package.json и запускаете `npm install`. На этот момент последняя версия — 6.19.5, npm её ставит вам.
2. **День 2, машина Б (машина вашего коллеги):** он клонирует репозиторий, видит `^6.19.3` и тоже запускает `npm install`. Но тут уже вышла 6.20.0 — и он получает её.
3. **Ада:** у вас работает, у него не работает. Или ещё хуже — тесты проходят у вас, но падают на CI/CD, где сборка происходит ещё в третий момент времени.

[Package-lock.json](https://docs.npmjs.com/about-semantic-versioning/) — это файл, который npm автоматически создаёт и обновляет при `npm install`. В нём записывается **точная версия каждого пакета и каждой его зависимости**, которая была установлена. Когда другой разработчик или CI запустит `npm install`, npm прочитает этот файл и установит **точно те же версии**, не смотря на то, что в package.json стоит `^`.

Вот почему lock-файлы **критично** коммитить в гит:

```bash
# ✓ правильно
git add package.json package-lock.json
git commit -m "Add dependency"

# ✗ неправильно
echo "package-lock.json" >> .gitignore
git add package.json
git commit -m "Add dependency"
```

Если вы не коммитнули lock-файл, каждая установка становится лотереей. Представьте, что вы используете `^` везде, и между вашим локальным обновлением и обновлением на боевом сервере прошло две недели. Вышло 50 новых версий зависимостей. Вероятность того, что ровно все они совместимы и никто не нарушил semver — стремится к нулю.

[По данным исследования](https://dev.to/wilsonwangdev/lock-files-and-package-manager-migration-a-practical-risk-analysis-2ejn), реальные пакеты постоянно нарушают семантическое версионирование: TypeScript вводит breaking changes в minor-релизах, PostCSS-плагины скрытно меняют CSS-output. Это означает, что lock-файл — это не просто удобство, это первая линия защиты.

## Практический ужас: когда версионирование ломает проект

**Сценарий 1: Забытый баг-фикс**

Вы заморозили версию `~express: 4.17.0` и забыли обновить. Выходит 4.17.5 с исправлением критической уязвимости. У вас она остаётся, потому что вы явно написали `~`, а не `^`. Три месяца спустя хакеры используют эту уязвимость. Не веселенько.

**Сценарий 2: Транзитивные зависимости**

Вы установили `some-lib` версии 1.2.0, которая зависит от `other-lib: ^2.3.0`. На момент вашей установки это была 2.3.5. Неделю спустя выходит `other-lib@2.4.0` с breaking change. Ваш коллега клонирует репо, запускает `npm install` без lock-файла — и получает 2.4.0, потому что каретка позволяет minor-обновления. Его сборка падает, ваша работает. Всё потому, что lock-файла нет.

**Сценарий 3: CI/CD рулетка**

На вашей машине `npm install`, на CI машине `npm install` (или хуже — без lock-файла). Разные версии, разные результаты. Код проходит локальные тесты, но падает в CI. Потом вы два часа гадаете, почему одно и то же работает по-разному.

## Разные lock-файлы для разных менеджеров

Если вы переходите с npm на yarn или на pnpm, важно знать:

- **npm** использует `package-lock.json`
- **yarn** использует `yarn.lock`
- **pnpm** использует `pnpm-lock.yaml`

Структурно они немного отличаются ([pnpm-lock.yaml](https://dev.to/_d7eb1c1703182e3ce1782/npm-vs-pnpm-vs-yarn-which-package-manager-should-you-use-in-2026-3o3o), например, оптимизирован под пнпм-ский content-addressable storage), но суть одна: фиксируют точные версии. Главное:

**Никогда не коммитьте lock-файлы разных менеджеров одновременно.** Если вы переходите с npm на pnpm, удалите старый `package-lock.json`:

```bash
rm package-lock.json
pnpm install
git add pnpm-lock.yaml package.json
git commit -m "Migrate to pnpm"
```

Если оставить оба файла, они будут конфликтовать, и коллеги будут в замешательстве.

## Типичные ошибки разработчиков

### Ошибка 1: Удаление lock-файла из .gitignore

```bash
# ✗ ошибка
echo "package-lock.json" >> .gitignore
```

Это превращает версионирование в казино. Коммитьте lock-файлы **всегда**.

### Ошибка 2: Ручное редактирование lock-файла

Lock-файлы автоматические. Не трогайте их руками. Если нужно обновить зависимость, используйте:

```bash
npm update package-name  # обновить в пределах диапазона
npm install package-name@desired-version  # установить конкретную версию
```

### Ошибка 3: Точная версия везде

```json
{
  "react": "18.2.0",
  "express": "4.17.1",
  "lodash": "4.17.21"
}
```

Это консервативно, но сложно. Вы упускаете баг-фиксы. Используйте `^` по умолчанию — так и задумано semver.

### Ошибка 4: Неправильная работа с lock-файлом при слиянии веток

Если у вас есть merge conflict в `package-lock.json`, не пытайтесь его разруливать вручную:

```bash
# ✗ неправильно: руками тыкать в lock-файл
git add package-lock.json  # после ручного редактирования

# ✓ правильно
git checkout --ours package-lock.json  # или --theirs
npm install  # npm автоматически обновит lock-файл
git add package-lock.json package.json
```

Npm сам разберётся с конфликтом при следующем `install`.

### Ошибка 5: npm install вместо npm ci в CI/CD

```bash
# ✗ может обновить lock-файл
npm install

# ✓ гарантирует точные версии
npm ci  # clean install
```

[`npm ci`](https://docs.npmjs.com/cli/ci) специально создана для CI-окружений — она устанавливает точно то, что в lock-файле, не обновляя его.

## Как правильно работать с версионированием

1. **Используйте `^` по умолчанию:**
   ```json
   {
     "react": "^18.2.0",
     "express": "^4.17.0"
   }
   ```
   Это позволит получать баг-фиксы и новые возможности автоматически, но защитит от breaking changes.

2. **Коммитьте lock-файл:**
   ```bash
   git add package.json package-lock.json
   ```

3. **Обновляйте зависимости через npm, не вручную:**
   ```bash
   npm update            # обновить в пределах диапазонов
   npm outdated          # посмотреть, какие обновления доступны
   ```

4. **В продакшене используйте `npm ci` вместо `npm install`:**
   ```bash
   npm ci
   ```

5. **Если нужна абсолютная стабильность, используйте `~` или точные версии** — но только для критических зависимостей:
   ```json
   {
     "critical-lib": "~1.2.3",
     "regular-lib": "^1.2.3"
   }
   ```

6. **Регулярно обновляйте зависимости**, но делайте это сознательно:
   ```bash
   npm audit              # проверить уязвимости
   npm audit fix          # автоматически исправить
   npm outdated           # посмотреть доступные обновления
   ```

## Итоговая чек-лист

- ✓ Понимаю, что MAJOR.MINOR.PATCH означает breaking/new/fix
- ✓ Использую `^` для гибкости, `~` для консервативности
- ✓ Коммичу package-lock.json в гит
- ✓ Использую `npm ci` в CI/CD, а не `npm install`
- ✓ Никогда не редактирую lock-файл вручную
- ✓ Не коммичу несколько lock-файлов разных менеджеров одновременно

Вот это и есть всё, что нужно для того, чтобы избежать часовых дебаг-сессий типа "работает на моей машине, но не на боевом".
