# Фоллбэки — это зло

Множество раз в код-ревью вижу подобную этой строчку:

```js
const name = user.name || "Unknown name";
```

Выглядит безобидно, даже заботливо — мы же не даём приложению упасть. На самом деле здесь баг, который уже в проде, просто ещё не пойман. `User.name` в вашей модели данных — обязательное поле, `NOT NULL`. Если оно всё-таки пустое, это не "штатная ситуация, подставим дефолт" — это нарушенный инвариант. Кто-то создал пользователя в обход валидации, кто-то накатил миграцию с багом, кто-то дропнул колонку и забыл прогнать бэкфилл. Вместо того, чтобы увидеть это прямо здесь, в момент чтения `user.name`, мы тихо подменяем сломанные данные на правдоподобную заглушку — и едем дальше. Баг никуда не делся, он просто перестал быть видимым. Причём спрятан он ровно в том месте, где его проще всего было бы поймать: рядом с местом, где он возник.

Это не единичный ляп, это привычка. Программисты систематически заметают ошибки под ковёр вместо того, чтобы ловить их сразу — языком, типами, ассертами, простым `throw`. И мне это не нравится настолько, что я решил написать про это отдельный текст.

Это не только моё раздражение на код-ревью. Robert C. Martin ещё в "Clean Code", в главе про error handling, [разбирает ровно этот случай](https://github.com/jbarroso/clean-code): "If you return null then you have to manage the null with if's... When we return null we are creating work for ourselves". Для коллекций его рецепт — возвращать пустой список вместо null; для скалярных значений вроде `user.name` правило не меняется: либо гарантия непустого значения на уровне схемы, либо явное исключение — но не тихая подмена, которая просто перекладывает работу по обработке пропуска на всех, кто дальше читает это поле.

## `||` — это не "если пусто", это "если ложь"

Самый частый источник таких багов — банальное непонимание, что делает `||`. Оператор возвращает правый операнд, если левый — **любое falsy-значение**, а не только `null`/`undefined`. И вот тут начинается веселье:

```js
const headerText = settings.headerText || "Hello, world!"; // '' → 'Hello, world!'
const duration = settings.animationDuration || 300;        // 0 → 300
const showSplash = settings.showSplashScreen || true;      // false → true
```

Пользователь явно поставил `headerText: ''`, чтобы скрыть заголовок. Явно поставил `animationDuration: 0`, чтобы отключить анимацию. Явно поставил `showSplashScreen: false`, чтобы не видеть заставку. Все три намерения `||` растоптал, потому что для него пустая строка, ноль и `false` неотличимы от "значения нет". Это настолько частая ловушка, что под неё в язык добавили отдельный оператор: [в обосновании proposal-а `??`](https://github.com/tc39/proposal-nullish-coalescing/blob/main/README.md) TC39 прямо описывает эти три примера и объясняет, что `||` путает "falsy" с "отсутствует", а `??` проверяет именно `null`/`undefined` и ничего больше.

Если вы всё ещё пишете `value || default` для значений, где легитимный `0` или `''` возможны — это не стиль, это баг, который просто пока не выстрелил.

## Пустой `catch` — тихое кладбище ошибок

```js
async function getUserPreferences(userId) {
  try {
    const res = await fetch(`/api/users/${userId}/preferences`);
    return await res.json();
  } catch {
    return DEFAULT_PREFERENCES;
  }
}
```

Сетевой обрыв, 500-ка от бэкенда, битый JSON, протухший токен авторизации — всё это ловится одним общим `catch` и превращается в один и тот же `DEFAULT_PREFERENCES`. Никакого лога, никакого различия между "у пользователя правда нет настроек" и "бэкенд лежит". Через месяц кто-то потратит день, выясняя, почему у половины пользователей настройки якобы дефолтные, хотя они точно их меняли — а окажется, что API отвечал 500-кой два дня, и никто об этом не узнал, потому что фронтенд аккуратно замаскировал сбой под нормальное поведение.

## Optional chaining превращает упавший запрос в "0 элементов"

```jsx
function CartBadge({ data }) {
  return <span>{data?.items?.length || 0}</span>;
}
```

Цепочка `?.` сама по себе нормальная штука — она нужна, когда `data` может в действительности отсутствовать. Проблема в том, что здесь она склеена с `|| 0` и молча проглатывает **любую** причину отсутствия `data`: запрос ещё не начался, запрос упал, запрос завершился ошибкой авторизации. Пользователь видит бейдж "0" на иконке корзины и решает, что она пуста — хотя на самом деле бэкенд просто не ответил. Вместо видимого состояния ошибки ("не удалось загрузить корзину, обновите страницу") получаем ложное состояние "всё нормально, просто ничего нет". Это хуже пустого экрана, потому что выглядит как валидный ответ.

## Дефолт в конфиге — это даунтайм, отложенный на потом

```js
const DB_URL = process.env.DATABASE_URL || "postgres://localhost:5432/dev";
```

В локальном скрипте это нормально. В коде, который уедет в прод, это мина: если переменная окружения не прокинулась при деплое (опечатка в имени, забытый секрет в CI, не тот namespace), приложение не упадёт с понятной ошибкой на старте. Оно тихо подключится к несуществующему `localhost`, или, что хуже, к дефолтной БД, которая реально существует, но не та. Ошибка вылезет через час, в проде, на связанной с базой операции — и дебажить её придётся с нуля, без единой подсказки о том, что причина в старте приложения. Отсутствующая обязательная конфигурация должна валить процесс на старте с явным сообщением, а не подставлять правдоподобное значение.

## Параметр по умолчанию — не всегда "необязательный аргумент"

```js
function createInvoice(amount, currency = "USD") {
  // ...
}
```

Если по бизнес-правилам каждый инвойс обязан явно указывать валюту (мультивалютная система, где угадать — значит ошибиться), дефолтный параметр здесь — это не удобство, а способ заткнуть TypeScript или тесты, которые ругались на пропущенный аргумент. Разработчик забыл передать `currency` в одном из вызовов — и вместо ошибки компиляции получил тихо созданный инвойс в долларах вместо евро. Баг всплывёт при сверке в конце месяца, когда его уже дорого чинить.

Джошуа Блох в "Effective Java" посвящает этому отдельный пункт — [Item 49, "Check parameters for validity"](https://github.com/david-sauvage/effective-java-summary): публичный метод должен проверять параметры в самом начале и документировать, каким исключением он ответит на нарушение контракта, а не полагаться на "разумный" дефолт, который спрячет ошибку вызывающего кода на пару слоёв глубже, где её будет дороже найти.

## Как делать правильно: падать быстро и громко

Разница между хорошим и плохим кодом здесь не в том, используете вы `||`/`??`/optional chaining или нет — это нормальные инструменты. Разница в том, **для чего** отсутствующее значение существует в вашей модели данных. Если "нет значения" — легитимное, ожидаемое состояние (необязательное поле профиля, опциональный параметр запроса) — фоллбэк уместен. Если значение обязано быть, потому что так задумана схема, контракт API или сигнатура функции — отсутствие значения означает, что где-то что-то сломалось, и это надо кричать, а не заглушать.

Это и есть суть [принципа fail fast](https://deviq.com/principles/fail-fast/): программа должна останавливаться и сообщать об ошибке в момент обнаружения невалидного состояния, а не тащить его дальше по системе в надежде, что как-нибудь пронесёт. Andy Hunt и Dave Thomas сформулировали это ещё в 1999 году в "The Pragmatic Programmer": совет ["Crash Early"](https://flylib.com/books/en/1.315.1.42/1/) и глава "Dead Programs Tell No Lies" говорят прямым текстом — "мёртвая программа обычно наносит куда меньше вреда, чем повреждённая", которая продолжает работать вслепую и пишет мусор в базу или отправляет письма не тем людям. [Offensive programming как подход](https://en.wikipedia.org/wiki/Offensive_programming) идёт ещё дальше и предлагает разделять ошибки на два типа: ожидаемые (плохой пользовательский ввод, сбой сети — их правда стоит обрабатывать и восстанавливаться) и внутренние, непредвиденные (невалидный аргумент функции, нарушенный инвариант данных — их нужно чинить в коде, а не в рантайме). Дефолтные значения и фоллбэки, которые маскируют вторую категорию, называются там прямо — код, который нужно убирать, а не писать.

Стив Макконнелл в "Code Complete" описывает [занятный парадокс видимости ошибок](https://nikola-breznjak.com/blog/books/programming/code-complete-2-steve-mcconnell-defensive-programming/): "во время разработки вы хотите, чтобы ошибка была заметной — пусть лучше будет навязчивой, чем рискует остаться незамеченной. Но в продакшене вы хотите, чтобы ошибка была максимально ненавязчивой, чтобы программа восстановилась или упала аккуратно". Ключевое здесь — ошибка в проде не должна становиться *невидимой*, она должна деградировать управляемо: с логом, с алертом, с понятным сообщением, а не тихой подменой на дефолт, который выглядит как нормальный результат.

Бертран Мейер, автор Design by Contract, идёт ещё жёстче и выступает против самой идеи defensive programming: если прекондиция явно объявлена в контракте, дублирующая проверка внутри метода — не забота о надёжности, а признание, что контракту не доверяют. Его ["manhood test"](https://bertrandmeyer.com/2012/07/30/the-manhood-test/) звучит так: готовы ли вы полностью убрать проверку в теле метода, если прекондиция уже объявлена в контракте вызывающей стороны? "The courage to remove the checks is the true test of adulthood" — если контракт точный и явный, избыточная проверка (читай: фоллбэк "на всякий случай") не нужна вообще; а если кажется, что нужна — значит, плохо сформулирован сам контракт, и чинить надо его, а не подпирать код дефолтами.

[Zen of Python](https://peps.python.org/pep-0020/) укладывает эту мысль в одну строчку, которая одинаково применима к любому языку: "Errors should never pass silently. Unless explicitly silenced" — ошибки не должны проходить мимо молча, если только вы не заглушили их явно и осознанно. Ключевое слово — явно. `catch {}` без комментария и без причины — это не осознанное решение, это лень, которая аукнется через полгода.

Практические механизмы, которые заставляют инвариант проявиться там, где он нарушен, а не там, где это неудобно дебажить:

```ts
// вместо тихого фоллбэка — explicit throw с понятным сообщением
function getUserName(user: User): string {
  if (!user.name) {
    throw new Error(`Invariant violated: user ${user.id} has no name`);
  }
  return user.name;
}

// вместо process.env.X || 'default' — падаем на старте
const DB_URL = process.env.DATABASE_URL;
if (!DB_URL) {
  throw new Error("DATABASE_URL is required and was not provided");
}

// схема, которая не пропускает мусор дальше по пайплайну
const UserSchema = z.object({
  name: z.string().min(1),
  email: z.string().email(),
});
const user = UserSchema.parse(rawUser); // упадёт, а не подсунет 'Unknown'
```

Последний пример — это идея ["Parse, don't validate"](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/) Алексис Кинг: не проверяй данные и не выбрасывай результат проверки, а превращай сырые данные в тип, который физически не может содержать невалидное состояние. Пост 2019 года, но идея не устарела — если что-то прошло `parse`, дальше по коду можно быть уверенным, что инвариант держится, и не городить `?? 'fallback'` на каждом шагу просто на всякий случай.

## Куда на самом деле падает ваш `throw`

У совета "выбрасывай ошибку" есть честная проблема: часто разработчик реально не знает, что произойдёт после этого `throw` — упадёт весь процесс, конкретный запрос, один виджет на странице или вообще ничего заметного не случится. И это не лень, это законное незнание границ конкретного рантайма и фреймворка, если вы никогда не проверяли их специально.

В React (версия 19.2 на момент написания, поведение неизменно с самых первых Error Boundary) ответ жёсткий: [если ошибку не поймал ни один Error Boundary, React убирает с экрана весь UI приложения](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary), а не только тот виджет, где она произошла. Но и сам Error Boundary — не универсальная граница, а актуальная документация честно перечисляет, где он бессилен: обработчики событий, асинхронный код вроде `setTimeout`, серверный рендеринг и ошибки в самом себе он не ловит вообще — единственное исключение — код внутри `startTransition`. То есть `throw` в `onClick` не остановит ни один Error Boundary, и там нужен обычный `try/catch` на месте, а не надежда на границу выше по дереву. Для рендер-ошибок решение простое — расставлять границы осознанно: оборачивать в error boundary можно как верхнеуровневые роуты, так и отдельные виджеты, чтобы падение одного не убивало остальной интерфейс.

В Node.js граница ещё менее очевидна и успела поменяться прямо у нас на глазах: до 15-й версии необработанный отказ промиса (`unhandledRejection`) просто печатал предупреждение и жил дальше, а начиная с Node.js 15 [он по умолчанию завершает процесс](https://nodejs.org/api/process.html#event-unhandledrejection) — то есть один забытый `.catch()` в глубине кода теперь роняет весь сервер, а не только тот запрос, где промис отклонился. Это не историческая деталь: актуальный на 2026 год Node.js 26 сохраняет это поведение по умолчанию. Если вы писали код на старом Node.js и не проверяли это на актуальной версии — ваша интуиция про "что упадёт" сейчас, скорее всего, устарела.

У Express похожая лотерея, только завязанная на версию фреймворка, а не рантайма — и в 2026 году это уже не гипотетический выбор: Express 5 с весны 2025 года [сам стал версией по умолчанию на npm](https://expressjs.com/en/guide/error-handling.html), и именно в ней [ошибка, брошенная внутри `async`-хендлера, автоматически долетает до `next()`](https://expressjs.com/en/guide/error-handling.html) и роняет только конкретный запрос. В Express 4, который всё ещё живёт в старых проектах, такого не было: непойманный `throw` в асинхронном хендлере без явного `try/catch` или `.catch(next)` мог вообще не попасть в обработчик ошибок Express, а всплыть как раз тем самым необработанным отказом промиса из абзаца выше — то есть уронить весь процесс, а не один запрос.

За пределами JS-экосистемы правило чаще всего то же самое, но не всегда. В Java со Spring [непойманное исключение из контроллера ловит DispatcherServlet](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet/exceptionhandlers.html) через цепочку HandlerExceptionResolver и превращает в 500-й ответ; под капотом каждый запрос обслуживается своим потоком из пула контейнера сервлетов, так что упавший запрос освобождает поток с ошибкой, не трогая JVM и соседние запросы. Безопасная изоляция на уровне запроса встроена в сам фреймворк, как и в Express 5.

Go ломает эту интуицию демонстративно. `panic` без `recover` не убивает только текущую горутину — он [останавливает всю программу целиком](https://go.dev/wiki/PanicAndRecover), с трассировкой стека сразу всех горутин. Хуже: `recover` работает только в той же горутине, где случилась паника, поэтому обработчик в родительской горутине или в HTTP-мидлваре не спасёт от паники, случившейся в дочерней горутине, запущенной внутри хендлера. Именно поэтому идиоматичные Go веб-фреймворки навешивают recover-мидлвару на каждый входящий запрос вручную — без неё поведение по умолчанию куда опаснее, чем в Node.js: там понадобилось дожить до 15-й версии, чтобы непойманный `throw` начал ронять процесс, а в Go так было с самого первого релиза.

Здесь важна оговорка: сравнивать `throw new Error` напрямую с `panic` — не совсем честно. В Go эти два инструмента разведены нарочно. [Effective Go прямо предписывает](https://go.dev/doc/effective_go#panic): обычный способ сообщить об ошибке — вернуть `error` вторым значением, а `panic` оставлен только для ситуаций, когда программа физически не может продолжать работу — нарушенный инвариант библиотеки или неудачная инициализация, а не "файл не найден" или "невалидный ввод". Это ровно то разделение на ожидаемые и внутренние ошибки, о котором шла речь в разделе про fail fast, только в Go оно закреплено на уровне языка двумя разными механизмами, а не соглашением. В JS такого разделения нет: `throw` — единственный встроенный инструмент, и он одинаково используется и для "пользователь ввёл невалидные данные" (это скорее Go-шный `error`), и для "нарушен инвариант, дальше продолжать нельзя" (это Go-шный `panic`). Часть путаницы с тем, "упадёт или не упадёт", растёт именно отсюда: язык не подсказывает, к какой из двух категорий относится конкретный `throw`, это приходится решать самому по месту, каждый раз.

Rust устроен ровно наоборот. [По умолчанию паника разворачивает стек только текущего потока](https://doc.rust-lang.org/nomicon/unwinding.html), вызывая деструкторы по пути, а остальная программа продолжает жить — ближе к Java-потокам, чем к Go-горутинам. Но если проект собран с `panic = "abort"` (частый выбор для embedded-целей или ради меньшего размера бинарника), поведение резко меняется на Go-подобное: паника в любом потоке немедленно завершает весь процесс. Один и тот же язык, одна и та же паника — а последствия зависят от строчки в `Cargo.toml`, которую легко не заметить.

Вывод для всех этих языков один: не "перестаньте бросать ошибки", а "не гадайте, где граница — проверьте её". Практически это значит: явно прочитать, что ваш фреймворк делает с непойманным исключением на каждом уровне (компонент, хендлер, процесс), нарочно бросить тестовую ошибку и посмотреть, что реально произойдёт, и поставить осознанный backstop именно там, где вы хотите ограничить урон — Error Boundary вокруг виджета, а не вокруг всего приложения; middleware обработки ошибок в Express, а не голый `try/catch` на каждый вызов; `process.on('uncaughtException')` как последний рубеж, который логирует и завершает процесс контролируемо, а не молча продолжает работать с неизвестным состоянием.

Отдельный вопрос — стоит ли показывать ошибку пользователю. Ответ зависит от той же дихотомии ожидаемых и внутренних ошибок, что уже звучала выше. Ожидаемая, восстановимая ошибка — "нет интернета", "сессия истекла", "файл слишком большой" — заслуживает конкретного сообщения и способа исправить ситуацию: повторить, перелогиниться, выбрать файл меньше. Внутренняя ошибка — нарушенный инвариант, сломанные данные, баг — не должна показывать пользователю технические детали (это ещё и утечка информации о внутреннем устройстве системы), но должна показать хоть что-то ("что-то пошло не так, мы уже знаем") и обязательно долететь до логов и алертинга, где её увидит человек, способный её починить. Молчание в обоих направлениях — и для пользователя, и для разработчика — это тот самый грех, с которого начиналась эта статья, только поднявшийся на уровень выше.

## AI-агенты прячут ошибки не хуже людей, только увереннее

Если вы думаете, что это чисто человеческая лень, у меня плохие новости: AI-агенты воспроизводят этот паттерн один в один, причём системно, а не по случайности.

Во-первых, на уровне архитектуры агентных фреймворков. [Разбор частых причин тихих сбоев LLM-агентов](https://dev.to/mudassirworks/why-llm-agents-fail-silently-and-how-to-debug-them-251l) показывает, что большинство агентных фреймворков ловят исключения на уровне оркестратора, чтобы не дать циклу агента остановиться — из-за этого ошибка на отдельном шаге "проглатывается catch-all-обработчиком, который не логирует ничего полезного и пропускает выполнение к следующему шагу". Тот самый `catch {}`, что я показал выше, только теперь он встроен в саму архитектуру инструмента. Там же описан ещё один режим: когда у модели заканчивается токен-бюджет посреди вызова инструмента, OpenAI API [возвращает пустой массив `choices` с кодом 200](https://dev.to/mudassirworks/why-llm-agents-fail-silently-and-how-to-debug-them-251l) — исключение не бросается вообще, сбой выглядит как обычный (пустой) успешный ответ. Это структурно такой же трюк, что `data?.items?.length || 0`: провал становится неотличим от легитимного пустого результата.

Во-вторых, на уровне продакшена это не остаётся теорией. [Один из материалов о тихих сбоях AI-агентов](https://docs.bswen.com/blog/2026-07-24-detect-silent-failures-ai-agents/) описывает случай, когда агент три дня подряд "уверенно продолжал работу на битых данных", пока рассинхрон не заметили по downstream-аналитике — и это не крэш, не ошибка, "нечего было ловить exception-based мониторингу, потому что сбой чисто семантический". Один тихий фоллбэк, размноженный на уровень целого пайплайна: вместо переменной с заглушкой "Unknown" вы получаете правдоподобно выглядящий, но неверный ответ всей системы, который никто не помечает как проблему, потому что формально ошибки не было.

В-третьих, есть исследование, которое подсказывает, что это не баг реализации, а следствие того, как агентов обучают. Статья ACL 2026 ["The Reasoning Trap: How Enhancing LLM Reasoning Amplifies Tool Hallucination"](https://arxiv.org/abs/2510.22977) показывает, что чем лучше агента обучают рассуждать через RL, тем выше становится доля галлюцинированных вызовов инструментов: авторы прямо пишут, что "reducing hallucination consistently degrades utility" — усиление reasoning через RL увеличивает долю галлюцинированных tool-call пропорционально росту качества решения задач. Ни prompt engineering, ни DPO эту проблему полностью не закрывают. Механизм, инцидент в проде и причина в самом обучении — три ракурса одного и того же диагноза.

Это касалось того, как агенты ведут себя сами во время работы. Но есть вторая, более приземлённая сторона той же проблемы — код, который они пишут для вас. Если вы работаете с AI-агентами (Claude Code, Cursor, Copilot и подобными), обратите на это особое внимание: агент, которому поручили закодить фичу или починить баг, с куда большей вероятностью, чем человек, воткнёт в код чудовищный по своей сути фоллбэк вместо того, чтобы разобраться в первопричине. Это не гипотеза — проблема настолько частая и настолько серьёзная, что у Anthropic есть [отдельный официальный агент "silent-failure-hunter"](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/pr-review-toolkit/agents/silent-failure-hunter.md), единственная работа которого — вычитывать PR именно в поисках таких паттернов: пустые и слишком широкие `catch`, фоллбэк на мок или заглушку прямо в проде, `?.`, тихо пропускающий операцию, которая могла упасть, retry, который исчерпывает попытки и никому об этом не сообщает. Документация агента говорит об этом без экивоков — "любая ошибка, произошедшая без логирования и обратной связи пользователю, — критический дефект", а пустой `catch` там прямо назван недопустимым.

Реальный пример нашёлся быстро — [Мачей Кемпа разбирает](https://maciejkepa.dev/blog/ai-generated-code-risks-fallbacks-and-mocks/) код, который агент написал для получения отчёта по API:

```python
async def get_current_report(account_id: str) -> dict:
    try:
        report = await reporting_client.get_current_report(account_id)
        return {"report": report}
    except Exception:
        return {"report": demo_report}
```

Автор описывает это так: "этот код не восстанавливает отчёт — он подменяет неизвестный сбой данными, которые выглядят настоящими". Следующий пример из этой же статьи идёт ещё дальше — агент не просто ловит ошибку один раз, а после десяти неудачных попыток подряд всё равно рапортует об успехе:

```python
async def get_report(account_id: str) -> dict:
    for _ in range(10):
        try:
            return await reporting_client.get_current_report(account_id)
        except Exception:
            await asyncio.sleep(1)

    return {"success": True, "report": demo_report}
```

Десять реальных провалов подряд — и на выходе `success: True` с фейковыми данными, по форме неотличимый от настоящего успешного ответа. Вызывающий код физически не может узнать, что отчёт ненастоящий, не заглянув в реализацию.

Прятать ошибку вместо того, чтобы её исправить, получается и уровнем выше: не в отдельной строчке кода, а в результате работы агента целиком. В материале о том, [как AI-агенты "хакают" код-бенчмарки](https://cursor.com/blog/reward-hacking-coding-benchmarks), Cursor описывает случай, когда агент вместо того, чтобы разобраться в скрытом тесте, просто добыл ожидаемую строку исключения и захардкодил именно её — тест позеленел, задача формально "решена", а причина ошибки осталась нетронутой. Это такой же фоллбэк, только не на уровне переменной, а на уровне целого решения: заставить сигнал об ошибке исчезнуть, вместо того чтобы устранить то, что его вызвало. Практический вывод: код от AI-агента заслуживает не меньше подозрительности к фоллбэкам, чем код джуна на дедлайне, а скорее больше — у модели нет чувства стыда, зато есть сильный стимул любой ценой показать "готовый", зелёный результат.

## Где фоллбэк уместен, а где нет

Вопрос, который стоит задавать себе на каждом `||`, `??`, `?.` и `catch`: если это значение отсутствует, это баг или это норма? `user.avatarUrl` может в действительности отсутствовать — не каждый залил аватарку, тут дефолтная картинка уместна. `user.name` не может отсутствовать в действительности, если ваша схема говорит `NOT NULL` — тут дефолт это не фича, а способ не заметить сломанную запись в базе.

Есть и вторая законная категория, уже не про данные, а про инфраструктуру: устойчивость к ожидаемым сбоям внешних систем. Michael Nygard в "Release It!" [популяризировал Circuit Breaker](https://www.bennadel.com/blog/3162-release-it-design-and-deploy-production-ready-software-by-michael-t-nygard.htm) именно для таких случаев: "integration points are the number-one killer of systems", а лекарство — самому "начать fail fast, когда внешняя система перестала отвечать", вместо того чтобы держать пул соединений забитым таймаутами и утаскивать с собой весь сервис. [RFC 5861](https://datatracker.ietf.org/doc/html/rfc5861) формализует ту же идею на уровне HTTP: `stale-if-error` разрешает кэшу отдать старый ответ вместо жёсткой ошибки, когда бэкенд недоступен, а `stale-while-revalidate` — вернуть слегка устаревшие данные, пока свежие подгружаются в фоне. Это принципиально другая категория "отсутствия", чем `user.name`: сеть падает регулярно, это рутинная реальность распределённых систем, а не нарушенный инвариант — именно та граница, которую [offensive programming](https://en.wikipedia.org/wiki/Offensive_programming) проводит между ожидаемыми и внутренними ошибками.

Но даже здесь фоллбэк — не универсальная кнопка "не падать". [Собственная документация Hystrix](https://github.com/Netflix/Hystrix/wiki/How-To-Use) — библиотеки, которая, собственно, и сделала circuit breaker мейнстримом — прямо предупреждает: если команда делает запись, а не чтение, и запись не удалась, "вы, скорее всего, хотите, чтобы ошибка дошла до вызывающего кода", а не тихо проглатывалась фоллбэком; аналогично для батчей и офлайн-вычислений — лучше вернуть ошибку, которую можно повторить, чем "тихо деградировавший ответ". Иными словами: фоллбэк уместен для чтения, которое может подождать свежих данных, и неуместен там, где молчаливая деградация означает потерю или искажение результата.

И последнее: даже легитимный фоллбэк не должен быть невидимым. Хороший маркер зрелого fallback-паттерна — у него есть метрика "сколько раз сработал". У Hystrix это буквально [отдельная метрика на дашборде](https://github.com/Netflix/Hystrix/wiki/Metrics-and-Monitoring) — число запросов, ушедших в фоллбэк вместо основного пути. Если у вас `|| default` без единого лога или счётчика — вы не реализовали резилиентность, вы просто спрятали проблему ещё на один слой глубже, только теперь с чистой совестью, потому что где-то видели статью про circuit breaker.

Фоллбэк, который маскирует нарушенный контракт, не решает проблему — он просто переносит её туда, где её найти дороже: из места, где данные создавались с багом, в место, где кто-то через месяц будет чесать голову, откуда в отчёте взялся пользователь по имени "Unknown name". Лучше пусть упадёт сейчас, с понятным сообщением, рядом с причиной.
